# Plan: NarSil for iOS

## Context
The Android port is a native touch UI (Kotlin/Compose) over a platform-neutral C bridge
(`android/app/src/main/cpp/narsil_*.c`, about 6,000 lines, with a pure C API in `narsil_bridge.h`).
The user has an iPhone available via a borrowed MacBook Air, and no Mac of their own. This dev
machine is Linux (no Xcode, no Swift).

`NarSil-continuous-ios/` (a checkout of the upstream NarSil iOS work) is a different approach:
the stock Angband SDL2 front end (`src/main-sdl2.c`, 12k lines, with `ON_IOS` touch-panel code) built for iOS by
CMake's Xcode generator. It ships a `.ipa` via `.github/workflows/ios.yaml`, built on a GitHub `macos-26`
runner and installed by sideloading (Sideloadly/AltStore), unsigned. The same checkout holds `scripts/build-ios.sh` and
`os/ios/Info.plist`. It is textui in an SDL window with a small on-screen key panel, so it is playable
but not the native UX we built.

What carries over from it:
- The CMake iOS toolchain `src/cmake/toolchain/ios.toolchain.cmake`, and the recipe: `-G Xcode`, `PLATFORM=OS64`,
  `GAMEDATA_IN_LIB`, `lib/` copied into the bundle as a resource.
- `Info.plist` settings: `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` (saves visible in the Files app),
  `UIStatusBarHidden`, `UIRequiresFullScreen`, orientations.
- `ON_IOS` hunks in `init.c`, `main.c`, `ui-init.c`: where user files go (the Documents directory).
- CI: GitHub Actions on macOS builds the `.ipa` without owning a Mac.
- Lesson: build with an Xcode whose SDK is below 27 (SDL2 lifecycle trap). Our app uses UIKit/SwiftUI
  scenes, so we avoid that issue, but keep the Xcode choice in mind.

What does not carry over: the SDL2 UI itself. We reuse the C core and bridge, not that front end.

## Recommended approach
Native iOS app in **SwiftUI** that calls the existing C bridge directly, the same way Compose calls it through JNI.
Do the iOS port in stages so there is something installable early:

### Phase 0: prove the toolchain (about 1 session, needs a Mac once)
- Build the continuous-ios SDL2 `.ipa` through its GitHub workflow (or on the borrowed Mac) and sideload it.
- Purpose: confirm signing/sideloading works, find the real iOS constraints (file paths, lifecycle, memory), and
  have a fallback textui build. No code of ours changes.
- Decide distribution (see Decisions).

### Phase 1: make the bridge build for iOS (Linux can do most of it)
- `narsil_bridge.c/.h`, `narsil_native.c` already compile on the host, so most is portable. Touch only the
  platform-specific spots: `__ANDROID__` guards (`narsil_bridge.h:208`, `narsil_native.c:783`), `ANGBAND_SYS`
  (`narsil_bridge.c:393`, "android"), and the log callback (already a function pointer: `.log`).
- New front-end-neutral layout: move `android/app/src/main/cpp/` bridge sources to a shared dir (e.g. `bridge/`)
  that both `android/` and `ios/` build, leaving `narsil_jni.c` Android-only. Keep Android building and the
  harness passing (`host-test.sh`, ASan and TSan) at every step.
- Build the core and bridge as static libs for iOS device and simulator with the existing CMake toolchain,
  packaged as one `NarSilCore.xcframework`. The bridge header is imported to Swift through a module map.
- Paths: pass the bundle's `lib/` as the read-only data dir and Application Support (or Documents, for the Files
  app) as the writable dir. The bridge already takes both as arguments (`GameLauncher.kt` does this on Android).
- Do not use Android's `SIGKILL`-on-background assumption: iOS suspends and may kill without notice, the same as
  Android, so the existing `bridge_service_save` and `between_commands` save points apply unchanged. Trigger
  `nb_request_save` from SwiftUI `scenePhase == .background`.

### Phase 2: Swift app skeleton
- `ios/NarSil.xcodeproj` generated by XcodeGen (`project.yml`, text, diff-able; no hand-edited pbxproj) or a
  Swift Package plus a thin app target. Bundle id and signing team are set in `project.yml`.
- `NarSilNative.swift`: thin wrappers over the C functions (mirror of `NarSilNative.kt`, 37 externals), with
  the game thread started by the bridge itself (pthread), not by Swift.
- `GameState.swift`: `ObservableObject` that polls the bridge on a `CADisplayLink` (the Kotlin side uses Choreographer)
  and pauses when inactive. Same cell-grid/meta/prompt generation counters.
- `Parse.swift`: port of `Parse.kt` (160 lines of pure parsing). **Reuse the recorded fixtures unchanged**
  (`android/app/src/test/resources/fixtures`, produced by `gen-fixtures.sh`) in an XCTest target, so the parsers
  are checked against the real game output on both platforms.
- Extend `check-bridge-constants.py` so it also compares the `NB_*` values with the Swift constants file, and
  run it in the Xcode build phase as in Gradle's `preBuild`.

### Phase 3: port the UI (the bulk; about 4,800 Kotlin lines → SwiftUI)
In this order, so it is playable early:
1. **Map and input:** `MapView` as a SwiftUI `Canvas` or `CALayer` drawing from `lib/tiles/microchasm/16x16.png`
   (CGImage tile crops, ASCII glyph fallback), tap/long-press/pinch, d-pad, action bar, status and message
   strips. (`MapView.kt` 348, `Dpad.kt`, `ActionBar.kt`, `StatusViews.kt`, `GlyphPainter.kt`)
2. **Prompts:** items, quantity, check, aim, direction, text, choice. (`Prompts.kt`, `ItemSheet.kt`)
3. **Panel:** Pack, Character, Skills, Abilities, Knowledge, Smithing, Options as tabs in one panel with
   swipe between tabs. (`Panel.kt`, `PackSheet.kt`, `KnowledgeScreen.kt`, `SmithSheet.kt`, `AbilitiesSheet.kt`,
   `OptionsScreen.kt`) The C side owns tab switching, so SwiftUI only renders the published tab.
4. **Birth, welcome, tutorial notes, death:** `ScreenSheet.kt`.
5. **Textui fallback** (`TerminalView.kt`) for the few screens that remain textui, plus a keyboard sheet.
6. **Extras:** Help, Settings, scumming, export/import of saves (`UIActivityViewController`/`fileImporter`
   instead of FileProvider), send logs, haptics (`UIImpactFeedbackGenerator` instead of VIBRATE).
- Keep the user's standing rules: instant UI with no animations, d-pad style, same layout (portrait and a landscape
  side rail), same gestures, same Help text. Use the Android screens as the spec; compare side by side.
- Dynamic Type and safe areas (notch/Dynamic Island) replace Android's insets code. Hardware keyboards via
  `onKeyPress` or `UIKeyCommand`.

### Phase 4: test and ship
- Linux: the harness (`host-test.sh`) still covers the whole C side. Pure-Swift logic (`Parse.swift`) is also
  built and tested on Linux if a Swift toolchain is installed (optional; not installed now).
- macOS CI (GitHub Actions `macos-26`): build the xcframework, run XCTest on the iOS simulator, build the app.
- On device: install while the game is not in the foreground; never touch the user's game. Test lifecycle:
  background, kill, relaunch, resume from save; rotate; low memory.
- Output: a signed `.ipa` (sideload) or a TestFlight build. Add a workflow like `ios.yaml` for it.

## Decisions for the user
1. **Distribution:** a free Apple ID can sideload, but the signing expires every 7 days (AltStore refreshes it).
   A paid developer account ($99/yr) gives TestFlight or 1-year signing. Recommend free sideload first.
2. **Mac access:** the Xcode project needs a Mac or CI to build. Recommend GitHub Actions for builds, plus
   the borrowed MacBook only for first signing, device logs and debugging.
3. **iPad:** support it from the start (adaptive layout) or iPhone-only. Recommend iPhone-first; the landscape
   rail already gives a decent iPad layout.
4. **Order vs NarSil-Q** (`plans/narsil-q.md`): the shared `bridge/` move in Phase 1 helps both. Recommend doing it
   before either.

## Risks
- **No local iOS compile:** every Swift/Xcode error is found on CI or the Mac, so iteration is slower. Mitigate
  by keeping Swift thin, porting screen by screen, and keeping parsers pure and fixture-tested.
- **Effort:** the UI port is the Kotlin line count again (about 4,800 lines), roughly the same effort as the Android UI.
- **Signing and 7-day expiry** for a free account; first run needs trusting the developer profile.
- **iOS memory/kill behaviour** differs from Android; keep saves frequent (already done).

## Verification
- Phase 0: `.ipa` installs and the SDL2 build runs on the iPhone.
- Phase 1: Android still builds, `host-test.sh` passes under ASan and TSan, `check-bridge-constants.py` passes,
  and `NarSilCore.xcframework` builds for device and simulator on CI.
- Phase 2: XCTest parses all fixtures (`everyPromptFixtureParses` equivalent) on CI.
- Phase 3: each screen compared with the Android one on the phone, then on the simulator and device.
- Phase 4: full play-through: birth, a dungeon level, panel tabs, save, background, kill, resume, death.
